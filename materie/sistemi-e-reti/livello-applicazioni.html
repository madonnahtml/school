Il livello delle applicazioni

Il livello più vicino a noi: quello dei programmi che usiamo ogni giorno (web, posta, trasferimento di file). Come sono organizzati, che cosa chiedono alla rete e come funziona FTP.

Le 5 cose che contano
  1. Un servizio si raggiunge con indirizzo IP + numero di porta: è il meccanismo dei socket.
  2. Client/server: un server sempre acceso con IP fisso; P2P: tutti pari, ognuno client e server.
  3. Un'applicazione sceglie il trasporto in base a affidabilità, banda, tempo e sicurezza: TCP se non può perdere dati, UDP se può.
  4. Il WWW è un ipertesto multimediale distribuito: il browser chiede un URL, il server risponde con il contenuto.
  5. FTP trasferisce file con due connessioni TCP: controllo (porta 21) e dati (porta 20). È in chiaro; FTPS lo cifra.

Le applicazioni di rete

Pagina 2

Nei modelli ISO/OSI e TCP/IP il livello applicazione realizza le applicazioni di rete usate dall'utente finale. È molto flessibile: si possono aggiungere sempre nuovi protocolli, quindi non esiste un numero preciso di protocolli. Tra i più noti:

Un'applicazione di rete è un insieme di programmi che girano contemporaneamente su due o più host (i computer collegati alla rete) e lavorano insieme usando risorse comuni, come gli archivi (database), attraverso la rete.

Porte e socket

Su un server possono girare tanti servizi insieme. Per scegliere quello giusto, oltre all'indirizzo dell'host serve il numero di porta:

  • per mandare un'email si usa SMTP sulla porta TCP 25;
  • per chiedere una pagina web si usa HTTP sulla porta TCP 80;
  • per tradurre un nome in indirizzo IP si chiede al DNS sulla porta UDP 53.
SocketIl processo in esecuzione su un host si identifica in modo univoco con la coppia indirizzo IP + numero di porta. Questo meccanismo si chiama socket.

L'indirizzo IP è l'indirizzo del condominio, la porta è il numero dell'appartamento: servono tutti e due per consegnare il pacco alla persona giusta.

Client/server e server farm

Pagine 2-3

Per progettare un'applicazione di rete, il primo passo è scegliere l'architettura: client/server, peer-to-peer (P2P) o ibrida (un misto).

Anche in TPSITQuesto argomento è spiegato anche in TPSIT: Sistemi distribuiti → Il modello client-server, con i livelli (tier) e altri esempi.

Nell'architettura client/server c'è sempre un server attivo che offre un servizio e aspetta che i client si colleghino per rispondere alle loro richieste. L'esempio tipico è il WWW: tanti server (al limite uno per ogni sito) hanno le pagine, statiche o dinamiche, e le mandano ai browser che le chiedono.

  • Il server deve essere sempre acceso e avere un indirizzo IP fisso (statico), così i client sanno dove trovarlo. I client di solito hanno un IP dinamico.
  • Un client non parla con gli altri client, solo con il server. Più client possono parlare con lo stesso server contemporaneamente.
Server farmSe troppi client chiedono insieme, il server va in congestione. Allora si crea una server farm: tanti server con un unico nome (hostname) ma più indirizzi IP, e le richieste vengono smistate tra loro senza che il client se ne accorga. Lo fanno Google, Amazon, Facebook e tutti i siti molto visitati.

Come un supermercato che apre più casse quando c'è la fila: l'insegna è una sola.

Le architetture peer-to-peer

Pagine 3-4

Anche in TPSITQuesto argomento è spiegato anche in TPSIT: Sistemi distribuiti → L'architettura P2P.

Nel P2P gli host sono coppie di peer (pari grado) che dialogano direttamente tra loro. Funziona come una comunità basata sul "dare e ricevere": ogni peer offre una risorsa e in cambio ne riceve altre. Esempi: eMule, Gnutella. Un sistema P2P è fatto di entità autonome che si auto-organizzano e condividono risorse distribuite; può essere completamente o parzialmente decentralizzato.

TipoCome funzionaEsempio
DecentralizzatoOgni peer è sia client sia server (servent). Non si può trovare una risorsa con un IP fisso: servono meccanismi di indirizzamento sopra il livello IP. Si condividono dati, memoria e banda, e il sistema si adatta da solo ai peer che entrano ed escono di continuo (churn), senza nessun server centrale.Gnutella
CentralizzatoUn compromesso: c'è un directory server che conserva l'indice (chi ha quali risorse) e risponde alle ricerche. I file però restano sui peer, che li scambiano direttamente tra loro.Napster
IbridoAlcuni peer, i supernodi (super-peer o ultra-peer), vengono scelti con un algoritmo di elezione e fanno da indice per un gruppo; gli altri sono leaf peer.–

Decentralizzato: chiedi a voce in cortile chi ha la figurina. Centralizzato: c'è una bacheca con scritto chi ha cosa. Ibrido: ogni classe ha un rappresentante che sa cosa hanno i compagni.

Che cosa chiedono le applicazioni al trasporto

Pagine 4-5

Tutti i protocolli applicativi devono trasferire messaggi da un punto all'altro della rete, e per farlo usano il livello di trasporto. Ogni applicazione sceglie il protocollo di trasporto in base a quattro esigenze:

Affidabilità

I dati arrivano tutti e giusti? Un file deve arrivare al 100%; una videochiamata può perdere qualche pezzo.

Banda (throughput)

Quanti bit al secondo servono. Una Web-TV in diretta ha bisogno di una banda minima garantita; posta e FTP si adattano a quella che c'è (sono "elastiche").

Temporizzazione

Quanto ritardo si può accettare. VoIP e giochi online vogliono ritardi piccolissimi.

Sicurezza

Cifratura per la riservatezza, e servizi di integrità e autenticazione da un capo all'altro (end-to-end).

TCP

Orientato alla connessione e affidabile: si usa quando perdere dati è inaccettabile (file, posta, web).

La raccomandata con ricevuta di ritorno.

UDP

Senza connessione, più veloce: si usa quando qualche perdita va bene (audio, video, giochi).

La cartolina: veloce, ma se si perde nessuno lo sa.

AttenzioneNé TCP né UDP garantiscono il tempo di consegna: TCP garantisce che il pacchetto arrivi, ma non quanto ci mette; UDP è più veloce, ma non promette niente. Il libro chiama TCP "Transfer Control Protocol": il nome esatto è Transmission Control Protocol.

L'architettura del WWW

Pagine 5-6

Anche in TPSITQuesto argomento è spiegato anche in TPSIT: Sistemi distribuiti → Applicazioni web.

WWW (World Wide Web) vuol dire "ragnatela grande come il mondo": un insieme di pagine multimediali (testo, audio, video) collegate tra loro, in cui ci si sposta in tanti modi. È un ipertesto multimediale distribuito.

  • Il client è il browser (Edge, Chrome, Firefox, Opera…): manda una richiesta URL e mostra le pagine.
  • Il server web ha le pagine del sito e manda la risposta con il contenuto. La prima pagina che arriva quando ti colleghi è la home page.
  • Le pagine sono scritte in HTML (un linguaggio di "contrassegno", a tag), con dentro anche script JavaScript (ECMAScript).

Che cosa succede quando scrivi http://www.mim.gov

  1. Il browser chiede la risorsa al server seguendo lo schema dell'URI, cioè con HTTP (prima il DNS trova l'indirizzo IP del nome).
  2. Il server del sito risponde con le informazioni richieste.
  3. Il browser legge la risposta, capisce che tipo di documento è (Content-Type) e manda altre richieste per le risorse collegate, come le immagini delle notizie.
  4. Il browser mostra la pagina, che contiene a sua volta dei link.
Identificazione

Ogni risorsa ha un indirizzo unico, l'URI o URL.

Interazione

Browser e server parlano con protocolli standard, con sintassi e significato precisi: clicchi un link e il browser va a prendere quella risorsa.

Formato

Nel messaggio ci sono meta-informazioni che dicono che tipo di documento è e come interpretarlo.

ApprofondimentoURL, HTTP e i suoi messaggi sono spiegati nei capitoli HTTP: la comunicazione nel Web e seguenti.

Il protocollo FTP

Pagine 6-7

FTP (File Transfer Protocol) è il protocollo del livello applicazione per trasferire file. Si basa su TCP ed è stato definito nel 1984 nell'RFC 959. È client/server: sul client gira un FTP client, sul server un FTP server.

A differenza degli altri protocolli, FTP usa due connessioni TCP separate, che lavorano in parallelo:

Connessione di controllo

Control connection o command channel, porta 21. Porta le informazioni di controllo: username, password, comandi (cambia cartella, scarica questo file…).

La telefonata con cui ordini.

Connessione dati

Data connection o data channel, porta 20. Serve solo a trasferire davvero i file.

Il furgone che porta il pacco.

Una sessione FTP

Sul canale di controllo il client manda comandi e il server risponde con codici di 3 cifre (come in HTTP):

←  220 Service ready                      il server è pronto
→  USER gda                               chi sono
←  331 User name OK, Password?
→  PASS xxxxx                             la password
←  230 User login OK
→  PORT 1267                              usa questa porta per i dati
←  150 Data connection open shortly
→  RETR /home/gda/libri/foundation.pdf    scarica questo file
   ════ trasferimento del file sulla connessione dati ════
←  226 Closing data connection
→  QUIT                                   ho finito
←  221 Service closing

FTP server e FTP client

Un FTP server (per esempio FileZilla Server) permette ai client di: scaricare e caricare file (download/upload), riprendere trasferimenti interrotti (resume), eliminare e rinominare file, creare cartelle e navigare tra le cartelle.

Per entrare serve l'autenticazione, e in base alle credenziali l'utente ha certi privilegi sul file system. Spesso c'è anche l'accesso anonimo, senza password, di solito in sola lettura.

Un FTP client (per esempio FileZilla, spesso gratuito) ha due parti: la parte di comunicazione, che realizza il protocollo FTP, e l'interfaccia utente, di solito grafica. I comandi di base sono:

ComandoChe cosa fa
openSi collega al server remoto
getTrasferisce un file dal server al client (download)
putTrasferisce un file dal client al server (upload)
dirElenca i file nella cartella corrente del server
cdCambia cartella sul server
byeSi disconnette

FTPS: FTP sicuro

FTP non cifra niente: username, password, comandi, codici di risposta e file viaggiano in chiaro e possono essere "sniffati". Per questo l'RFC 4217 ha aggiunto a FTP uno strato di cifratura SSL/TLS e nuovi comandi: è il protocollo FTPS. Nei programmi un lucchetto indica che il trasferimento è sicuro.

Riassunto in 3 righe

  1. Il livello applicazione contiene i protocolli dei servizi (HTTP, SMTP, FTP, DNS, Telnet, SNMP); un servizio si raggiunge con IP + porta, il socket.
  2. Client/server: server sempre acceso con IP fisso (e server farm se c'è troppo traffico); P2P decentralizzato, centralizzato (directory server) o ibrido (supernodi). Le applicazioni scelgono TCP o UDP in base ad affidabilità, banda, tempo e sicurezza.
  3. Il WWW è un ipertesto distribuito tra browser e server web; FTP trasferisce file con una connessione di controllo (21) e una dati (20), in chiaro: FTPS aggiunge la cifratura.
★Mini-sfida ragionamento
  1. Perché il server di un sito deve avere un IP fisso e il tuo PC no?
  2. Per ognuna di queste applicazioni sceglieresti TCP o UDP? a) scaricare un PDF; b) una videochiamata; c) mandare un'email; d) un gioco online sparatutto.
  3. In una sessione FTP, su quale connessione passa la password? E il file?
  4. Perché si usa FTPS invece di FTP?
Soluzione
  1. Perché i client devono sapere dove trovarlo ogni volta. Il tuo PC non viene cercato da nessuno: è lui a chiedere, quindi può cambiare IP.
  2. a) TCP (il file deve arrivare intero); b) UDP (meglio perdere un pezzetto che arrivare in ritardo); c) TCP; d) UDP (conta il tempo).
  3. La password passa sulla connessione di controllo (porta 21), il file sulla connessione dati (porta 20).
  4. Perché FTP manda tutto in chiaro, password comprese; FTPS aggiunge la cifratura SSL/TLS.
