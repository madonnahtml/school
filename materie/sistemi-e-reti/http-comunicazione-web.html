HTTP: la comunicazione nel Web

Come parlano il browser e il server: chi fa cosa, come si scrive un indirizzo, come si apre una connessione e com'è fatto, riga per riga, un messaggio HTTP.

Le 5 cose che contano
  1. Il client (browser) è attivo e chiede; il server è passivo, ascolta sulla porta 80 e risponde.
  2. Un URL si scrive schema://host:porta/path?query#fragment.
  3. HTTP sta nel livello applicazione e usa TCP; è stateless (non ricorda le richieste precedenti).
  4. HTTP/1.0 apre una connessione per ogni oggetto; HTTP/1.1 la tiene aperta (persistente) e può usare il pipelining.
  5. Ogni messaggio è: riga iniziale + header + riga vuota + body.
Lo stesso argomento in TPSITMolte di queste cose ci sono anche in TPSIT: Il protocollo HTTP. Qui le trovi con gli esempi del libro di Sistemi e Reti e con gli header spiegati uno per uno.

Client e server

Pagine 44 e 46

Il Web si basa sul modello client/server.

Client: elemento attivo

È il browser. Prende l'iniziativa: usa un URL per indicare la risorsa, la chiede al server con HTTP e poi la mostra.

Il cliente che entra in pizzeria e ordina.

Server: elemento passivo

È il web server (HTTP server). Resta in ascolto su una porta TCP aspettando i client, e fornisce le pagine e le risorse richieste.

Il pizzaiolo che aspetta gli ordini.

Più precisamente, per HTTP il "client" è il programma che apre una connessione per mandare richieste, e il "server" è il programma che accetta connessioni e manda risposte.

ProtocolloUn insieme di regole che stabilisce quali messaggi si possono scambiare e quali sono le risposte giuste. HTTP (HyperText Transfer Protocol) è il protocollo per inviare e ricevere le risorse del Web.

Il Web è nato unendo tre tecnologie: WWW = HTML + URL + HTTP. HTML descrive le pagine, URL dice dove sono, HTTP le trasporta. Le versioni principali sono HTTP/1.0 (1996) e HTTP/1.1 (1999).

URI, URL e URN

Pagine 44-45

HTTP trasporta risorse, non solo file: una risorsa può essere un documento, un'immagine, un servizio, il risultato di uno script… Ogni risorsa ha un indirizzo, l'URI.

URI

Uniform Resource Identifier: il nome generico per tutti gli identificatori di risorse.

URL

Uniform Resource Locator: dice dove si trova la risorsa e con che protocollo prenderla (https://miosito.it/home.htm).

URN

Uniform Resource Name: dà alla risorsa un nome che resta valido anche se la risorsa non è più disponibile.

URI = URL + URN: URL e URN sono due sottoinsiemi degli URI.

L'URN è come il codice fiscale (ti identifica per sempre), l'URL è come l'indirizzo di casa (dice dove trovarti oggi).

Le parti di un URL

schema://host:porta/path?query#fragment

https://ospite:pippo@www.istruzione.it:443/uploads/esercitiamoci.html?pagina=3#area_tutor

HTTP nella pila TCP/IP

Pagine 45-46

  1. 4ApplicazioneHTTP, DNS: qui lavora HTTP
  2. 3TrasportoTCP: consegna affidabile dei dati
  3. 2InternetIP: trova la strada tra le reti
  4. 1Interfaccia di reteEthernet, Wi-Fi (IEEE 802.11), LTE

HTTP è un protocollo di testo del livello applicazione: i messaggi sono righe di caratteri ASCII che si possono leggere. Sotto, TCP si occupa di farli arrivare interi e in ordine.

Sessioni e stateless

Per comunicare HTTP usa le sessioni:

  1. il server è in ascolto sulla porta 80;
  2. il client apre una connessione TCP verso quella porta e il server la accetta;
  3. il client manda la richiesta (request) con l'URL;
  4. il server manda la risposta (response) con il file e, con HTTP/1.0, chiude subito la connessione.
Stateless (senza memoria di stato)Né il client né il server ricordano, a livello di protocollo, i messaggi scambiati prima: ogni richiesta è nuova. Per questo, per ricordarsi di te (login, carrello), i siti usano i cookie.

Come un distributore automatico: non sa che sei lo stesso di cinque minuti fa.

Le connessioni: HTTP/1.0, HTTP/1.1 e pipelining

Pagine 47-49

Prima di parlare, client e server aprono una connessione TCP con tre messaggi (SYN, SYN-ACK, ACK: la "stretta di mano a tre"). Alla fine la chiudono con altri messaggi (FIN). Aprire e chiudere costa tempo.

Esempio: una pagina con 2 immagini

Chiediamo www.istitutovolta.edu/informatica/home.index, una pagina HTML con alcune immagini PNG. Con HTTP/1.0:

  1. il client apre una connessione TCP con il server sulla porta 80; il server, in attesa, la accetta;
  2. il client manda la richiesta con l'URL;
  3. il server manda la risposta con la pagina;
  4. il server chiude la connessione;
  5. il client legge l'HTML (parsing) e scopre che servono le immagini;
  6. ripete i passi 1-5 per ogni immagine.
VersioneCome funzionaParagone
HTTP/1.0 (non persistente)Una connessione TCP per ogni oggetto, uno dopo l'altro: apri, chiedi, ricevi, chiudi.Telefoni in pizzeria, ordini una pizza, riattacchi; richiami per la seconda.
HTTP/1.1 (persistente)Il server lascia aperta la connessione: tutti gli oggetti della pagina passano sulla stessa.Una sola telefonata per tutte le pizze, ma una alla volta: aspetti la conferma prima di dire la prossima.
HTTP/1.1 con pipeliningIl client manda più richieste di fila senza aspettare le risposte.Detti tutto l'ordine di fila e poi ascolti le conferme.

Persistente non incanalata

Il client manda una nuova richiesta solo dopo aver ricevuto la risposta precedente.

Persistente incanalata (pipeline)

Le richieste si mettono in coda una dopo l'altra (back-to-back); il server risponde nello stesso ordine. È il default di HTTP/1.1.

Perché lo stesso ordine?Nel pipelining le risposte devono tornare nell'ordine delle richieste, perché non c'è un modo per dire "questa risposta è per quella richiesta". La connessione persistente si chiude da sola se resta inutilizzata per un certo tempo: l'intervallo di timeout.

Com'è fatto un messaggio HTTP

Pagina 49

Richiesta e risposta hanno la stessa forma:

<riga iniziale, diversa tra richiesta e risposta>
Intestazione1: valore1
Intestazione2: valore2
Intestazione3: valore3
                                  ← riga vuota
<corpo del messaggio, facoltativo>
  1. 1Riga inizialeObbligatoria. Nella richiesta: metodo, risorsa, versione. Nella risposta: versione, codice di stato, frase.
  2. 2Intestazione (header)Facoltativa: righe nome: valore.
  3. 3Riga vuotaObbligatoria: dice "gli header sono finiti".
  4. 4Corpo (body)Facoltativo: i dati. La sua lunghezza è scritta in Content-Length.
MIMEIl tipo MIME (Internet media type) dice che tipo di file è, con due parti classe/formato: text/html, text/plain, image/png, audio/mpeg, application/json.

La richiesta (request)

Pagine 50-51

<Method> <URI> <Version>      // riga di richiesta
[Header]                       // intestazione
CRLF                           // riga vuota
[Body]                         // corpo del messaggio

La riga di richiesta

  • Il metodo, sempre in MAIUSCOLO (è case sensitive). Quali esistono dipende dalla versione:
    VersioneMetodi
    HTTP/0.9solo GET
    HTTP/1.0GET, HEAD, POST, PUT, DELETE, LINK, UNLINK
    HTTP/1.1GET, HEAD, POST, PUT, DELETE, OPTIONS, TRACE, CONNECT
  • L'URI della risorsa. Per TRACE e OPTIONS si può non indicare una risorsa e scrivere un asterisco *.
  • La versione, scritta tutta maiuscola: HTTP/1.0 o HTTP/1.1.
GET /percorso/file.html HTTP/1.1
│   │                   └─ versione
│   └─ URI: il file file.html nella cartella /percorso della radice del server
└─ metodo
CRLFÈ l'"a capo" dei messaggi HTTP: due caratteri ASCII, CR (Carriage Return, torna a inizio riga) e LF (Line Feed, scendi di una riga). Ogni riga finisce con CRLF; una riga fatta solo di CRLF è la riga vuota che chiude gli header.

Header e body della richiesta

Ogni header è una riga nome_header: valore + CRLF. Gli header più comuni nelle richieste sono User-Agent (il browser), Host (il server) e Accept (i tipi MIME accettati).

GET / HTTP/1.1
Accept: image/gif, image/jpeg, image/png, */*
Accept-Language: it
Accept-Encoding: gzip, deflate
Host: www.istitutovolta.gov.edu
If-Modified-Since: Fri, 14 Mar 2021 10:54:03 GMT
User-Agent: Mozilla/4.0 (compatible; MSIE 5.5; Windows NT 5.0)
                                   ← riga vuota (CRLF): fine del messaggio

Il body della richiesta (entity body) contiene i dati da mandare: l'input di un programma o informazioni da salvare sul server, per esempio i campi di un form con POST. Con GET il body non c'è.

Che cosa fa il server

Ricevuta la richiesta, il server fa quello che serve per preparare la risorsa: a volte basta leggere un file, a volte deve eseguire uno script lato server (server side) con tecnologie come CGI, PHP, ASP, JSP o Perl. Poi manda la risposta. Com'è fatta la risposta e quali metodi esistono è spiegato in HTTP: i metodi (verbi).

Gli header HTTP

Pagine 53-54

Gli header sono coppie Nome: valore in formato ASCII. Si dividono in quattro gruppi:

Generali

Valgono sia per la richiesta sia per la risposta.

Di richiesta

Li mette il client: informazioni sulla richiesta.

Di risposta

Li mette il server: informazioni su di sé e sulla risposta.

Dell'entità

Descrivono il body (o la risorsa richiesta).

Header generali

HeaderSignificato
DateData e ora della trasmissione.
MIME-VersionLa versione MIME usata (di solito 1.0).
Transfer-EncodingCome è codificato o compresso tutto il messaggio: chunked, compress, deflate, gzip, identity.
Cache-ControlCome la risorsa può essere salvata nella cache.
ConnectionKeep-Alive (la connessione resta aperta dopo la risposta) o Close (si chiude).
Chunked: a pezzettiServe quando il server non sa prima quanto sarà lunga la risposta, per esempio l'output di uno script PHP o JSP. La risposta parte a pezzetti (chunk), ognuno preceduto dalla sua lunghezza in esadecimale; un pezzetto di lunghezza 0 vuol dire "ho finito".

Come una lettera scritta e spedita un foglio alla volta, con l'ultimo foglio bianco per dire "fine".

Il tipo più comune è Basic: username e password uniti dai due punti e codificati in Base64. Ce ne sono altri, registrati dall'IANA (es. AWS4-HMAC-SHA256 per i server Amazon). Tutto spiegato in L'autenticazione con HTTP.

Header dell'entità

HeaderSignificato
Content-TypeIl tipo MIME del body: testo, immagine PNG, suono WAV, filmato MPG… Obbligatorio se c'è un body. Es. Content-Type: text/html.
Content-LengthLa lunghezza del body in byte. Obbligatorio con le connessioni persistenti: è così che il client sa dove finisce una risposta e inizia la successiva.
Content-EncodingLa compressione del body, es. gzip: HTML, CSS e JavaScript pesano meno.
Content-Language, Content-Location, Content-Base, Content-MD5, Content-RangeLingua, URL della risorsa, URL di base, digest MD5 per controllare i dati, parte della risorsa inviata.
ExpiresLa data di scadenza: dopo, la risorsa non è più valida e va richiesta di nuovo o tolta dalla cache.
Last-ModifiedData e ora dell'ultima modifica: serve a capire se la copia nella cache è ancora buona.

Riassunto in 3 righe

  1. Il browser (client attivo) chiede risorse identificate da URL (schema://host:porta/path?query#fragment) a un server passivo in ascolto sulla porta 80; URI = URL + URN.
  2. HTTP sta nel livello applicazione sopra TCP, è stateless; HTTP/1.0 apre una connessione per oggetto, HTTP/1.1 usa connessioni persistenti e pipelining (risposte nello stesso ordine).
  3. Un messaggio è riga iniziale + header nome: valore + riga vuota (CRLF) + body; gli header sono generali, di richiesta, di risposta e dell'entità (Content-Type, Content-Length…).
★Mini-sfida ragionamento
  1. Dividi nelle sue parti l'URL https://www.scuola.it:8443/orari/classe5.php?giorno=lun#pomeriggio.
  2. Una pagina ha 1 file HTML e 4 immagini. Quante connessioni TCP apre HTTP/1.0? E HTTP/1.1 persistente?
  3. Nella richiesta qui sotto trova l'errore: get /index.html http/1.1.
  4. A che cosa servono Content-Type e Last-Modified?
Soluzione
  1. Schema https; host www.scuola.it; porta 8443 (diversa dal default 443); path e file /orari/classe5.php; query giorno=lun; fragment pomeriggio.
  2. HTTP/1.0: 5 connessioni, una per oggetto. HTTP/1.1 persistente: 1 sola connessione per tutti e 5.
  3. Metodo e versione vanno in maiuscolo: GET /index.html HTTP/1.1.
  4. Content-Type dice il tipo MIME del body (per esempio text/html), così il browser sa come mostrarlo. Last-Modified dice quando la risorsa è cambiata l'ultima volta, così si capisce se la copia nella cache è ancora valida.
