Il protocollo HTTP

UD2, lezione 1: come browser e server web si parlano. Vediamo gli indirizzi (URL e URI), come si apre e si chiude una connessione e come sono fatti i messaggi di richiesta e di risposta.

In una frase HTTP (HyperText Transfer Protocol) è il protocollo con cui un client (il browser) chiede risorse web a un server e il server gliele manda. Le richieste si chiamano request, le risposte response.

Client attivo, server passivo

Il web si basa sul modello client/server. In HTTP i due ruoli sono molto netti:

Client: elemento attivo

È il browser. Prende l'iniziativa: apre la connessione, usa un URL per indicare cosa vuole, chiede la pagina e poi la mostra.

È il cliente che entra in negozio e chiede.

Server: elemento passivo

È il web server (o HTTP server). Resta in ascolto su una porta TCP (di solito 80) e risponde solo quando qualcuno gli chiede qualcosa.

È il commesso dietro al bancone che aspetta.

Risorse, non solo file

HTTP trasmette risorse. Una risorsa può essere un file (una pagina HTML, un'immagine), ma anche qualcosa generato al momento: il risultato di una ricerca in un database, l'output di un programma sul server, un documento disponibile in più lingue. Ogni risorsa è identificata da un URI o da un URL.

URI, URL e URN

URI

Uniform Resource Identifier: una stringa che identifica in modo univoco una risorsa, online o offline.

URL

Uniform Resource Locator: un URI che dice dove si trova la risorsa e come raggiungerla.

URN

Uniform Resource Name: un URI che dà un nome stabile alla risorsa, valido anche se la risorsa non è più disponibile.

Per capire la differenzaPensa a un libro. Il suo codice ISBN è un URN: lo identifica per sempre, ma non ti dice dove trovarlo. "Biblioteca civica, scaffale 3, ripiano 2" è un URL: ti dice dove andare a prenderlo. Entrambi sono URI: URI = URL + URN.

Un URI è formato da due parti separate dai due punti: lo schema e la parte specifica.

EsempioSchemaTipo
isbn:0-395-36341-1isbnURN: il nome di un libro
tel:+1-816-555-1212telURI di un numero di telefono
https://example.com/blog/article/123httpsURL: dove si trova una pagina web

Le parti di un URL

La sintassi completa è:

https://ospite:pippo@www.istruzione.it:443/uploads/esercitiamoci.html?pagina=3#area_tutor

Dove sta HTTP nella pila TCP/IP

HTTP è un protocollo di livello applicazione e si appoggia sotto di sé su TCP (trasporto), che a sua volta usa IP. È un protocollo testuale: i messaggi sono righe di testo leggibili da una persona.

  3. 2InternetIP (IPv4, IPv6)
  4. 1Accesso alla reteEthernet, Wi-Fi (IEEE 802.11), LTE · indirizzi MAC

Come avviene una comunicazione

HTTP comunica per sessioni. Ogni sessione segue sempre gli stessi passi:

  1. Il server è in ascolto sulla porta 80. Il client apre una connessione TCP verso quella porta.
  2. Il server accetta la connessione. Il client invia la sua request, che contiene l'URL della risorsa.
  3. Il server invia la response con la risorsa e, nel caso più semplice, chiude subito la connessione TCP.

La stretta di mano TCP

Prima di qualunque messaggio HTTP, client e server si scambiano 3 segmenti TCP per aprire la connessione (il three-way handshake). Alla fine, un altro scambio di segmenti la chiude.

Come una telefonataSYN: "Pronto, mi senti?" · SYN, ACK: "Sì, ti sento. E tu mi senti?" · ACK: "Sì!". Solo dopo si comincia a parlare.

HTTP è stateless (senza stato)

Né il client né il server ricordano i messaggi scambiati prima: ogni richiesta è indipendente dalle precedenti. Per il server, la tua seconda richiesta arriva da uno sconosciuto, proprio come la prima.

Approfondimento: e allora come fa un sito a ricordarsi di me?Con i cookie. Il server manda nella response un header Set-Cookie con un codice; il browser lo salva e lo rimanda a ogni richiesta successiva nell'header Cookie. Così login e carrello funzionano anche se HTTP, da solo, non ricorda niente.

Esempio: una pagina con delle immagini

Vogliamo la pagina www.istitutovolta.edu/informatica/home.html, che contiene un file HTML e alcune immagini PNG.

  1. Il client apre una connessione TCP con www.istitutovolta.edu sulla porta 80. Il server, che era in attesa, l'accetta.
  2. Il client invia una request con il path /informatica/home.html.
  3. Il server legge la richiesta, prende il file e lo rimanda in una response.
  4. Il server chiude la connessione TCP.
  5. Il client riceve l'HTML, lo legge (parsing) e scopre che servono anche delle immagini.
  6. I passi da 1 a 4 si ripetono per ogni immagine.

Ripetere tutto per ogni file è lento: per questo sono nate le versioni successive di HTTP.

HTTP/1.0 e HTTP/1.1: le connessioni

VersioneAnnoConnessione
HTTP/1.01996Non persistente: una connessione TCP per ogni coppia richiesta/risposta.
HTTP/1.11999Persistente: il server lascia aperta la connessione e la riusa per più richieste.
AttenzioneLe slide dicono che HTTP/1.1 permette anche di "criptare i dati". In realtà la cifratura non dipende dalla versione: la fornisce HTTPS, cioè HTTP che viaggia dentro una connessione protetta con TLS (porta 443).

Esempio delle slide: la pagina page.html contiene due immagini, hpface.jpg e castle.gif. Servono quindi 3 richieste.

HTTP/1.0: una connessione per ogni file

HTTP/1.1: connessione persistente

Il server lascia aperta la connessione TCP dopo la risposta, e tutte le richieste successive la riusano. Una pagina fatta di tanti file può arrivare con una sola connessione. Il server la chiude da solo se resta inutilizzata per un certo tempo, l'intervallo di timeout.

Ci sono due modi di usare la connessione persistente:

Non incanalata

Il client manda la richiesta successiva solo dopo aver ricevuto la risposta alla precedente.

Ordini un piatto, aspetti che arrivi, poi ordini il prossimo.

Incanalata (pipelining)

Il client manda più richieste di fila senza aspettare. Le richieste finiscono in una coda, la pipeline, e le risposte tornano nello stesso ordine.

Ordini tutto insieme e i piatti arrivano in ordine.

Il problema del pipelining

Le risposte devono tornare nell'ordine delle richieste, perché in HTTP/1.1 non c'è un modo per abbinare una risposta alla sua richiesta. Se la prima risposta è lenta, blocca tutte le altre anche se sono già pronte: si chiama head-of-line blocking (HOL).

Come alla cassa: se il primo della fila ha il carrello pieno, aspettano tutti.

Da sapere per la verificaLe slide dicono che HTTP/1.1 usa di default la connessione incanalata. Nella pratica, però, i browser moderni disattivano il pipelining per problemi di compatibilità e di sicurezza, e usano la connessione persistente non incanalata.

I messaggi HTTP

Request e response hanno la stessa forma, fatta di quattro parti:

  1. una riga iniziale (diversa tra richiesta e risposta);
  2. le intestazioni (header), una per riga, facoltative;
  3. una riga vuota, che segna la fine delle intestazioni;
  4. il corpo (body), facoltativo.
<riga iniziale>
Intestazione1: valore1
Intestazione2: valore2

<corpo del messaggio, facoltativo>

Ogni riga finisce con CRLF, cioè i due caratteri "a capo" \r\n (carriage return + line feed). Ogni header ha il formato nome_header: valore.

La richiesta (request)

È il messaggio di testo che il client invia al server. Ha tre elementi: riga di richiesta, header e corpo.

La riga di richiesta

Contiene tre campi separati da uno spazio: metodo, URI della risorsa e versione del protocollo.

GET /percorso/file.html HTTP/1.1

I metodi

Il metodo dice al server cosa vogliamo fare con la risorsa.

MetodoCosa faEsempio
GETChiede una risorsa. Non ha corpo.Aprire una pagina
HEADCome GET, ma il server risponde solo con gli header, senza corpo.Controllare se un file è cambiato
POSTInvia dati al server nel corpo della richiesta, perché li elabori.Inviare un modulo di login
PUTCrea o sostituisce la risorsa all'URI indicato.Caricare un file
DELETECancella la risorsa.Eliminare un post
OPTIONSChiede quali metodi il server accetta per quella risorsa.–
TRACEIl server rimanda indietro la richiesta così come l'ha ricevuta (diagnostica).–
CONNECTApre un "tunnel" attraverso un proxy.HTTPS tramite proxy

GET

I dati viaggiano nell'URL, nella query: /cerca?q=pizza.

Si vedono, finiscono nella cronologia e si possono condividere. Adatto per leggere, come una ricerca.

POST

I dati viaggiano nel corpo del messaggio, non nell'URL.

Adatto per inviare dati o modificarli: login, registrazioni, ordini. Le password non devono mai finire nell'URL.

Con GET non c'è corpo: dopo gli header c'è solo la riga vuota.

Esempio: una richiesta POST con i dati di un modulo

POST /pagina.jsp HTTP/1.1
Host: corsouniversitario.it
Content-Type: application/x-www-form-urlencoded
Content-Length: 27
Connection: keep-alive

user=denny&citta=genova

Dopo la riga vuota c'è il corpo (entity body) con i dati del modulo. Il server sa quanto è lungo grazie a Content-Length.

La risposta (response)

È organizzata come la richiesta. L'unica differenza è la prima riga: al posto della riga di richiesta c'è la riga di stato (status line).

HTTP/1.1 200 OK

Il numero di tre cifre dice com'è andata. La prima cifra indica la categoria. Questa tabella è un'aggiunta alle slide: è molto utile da sapere.

Il corpo della risposta

Il body della response è quasi sempre presente e contiene di solito la pagina HTML richiesta. Può però contenere qualunque altro tipo di dati, indicato da Content-Type.

Risposte in formato JSON

Le app e i siti moderni spesso non chiedono una pagina, ma solo dati. Il client lo dice con l'header Accept: application/json:

POST pagina.jsp HTTP/1.1
Host: corsouniversitario.it
Accept: application/json, text/plain, */*
Connection: keep-alive

user=denny&citta=genova

E il server risponde con i dati in formato JSON nel corpo:

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 102

{
  "ID": 215,
  "Username": "denny",
  "Cognome": "Botta",
  "Cod_impiego": "AE34y",
  "Citta": "Genova",
  "Email": "daniele.botta67@gmail.com"
}
JSONJavaScript Object Notation: un formato di testo per i dati, fatto di coppie "chiave": valore tra parentesi graffe. È facile da leggere sia per le persone sia per i programmi.

Mappa riassuntiva

  • URI si divide in URL e URN, e indica le risorse nel modello client/server.
  • Su questo modello si basa HTTP, che appartiene all'application layer e si appoggia su TCP.
  • Versioni: 0.9, 1.0 e 1.1, che permette la connessione permanente e il pipelining.
  • HTTP si basa su messaggi, che sono request o response, formati da riga iniziale (request line o status line), header lines e body.

Esercizi

01Scomponi l'URL facile

Indica schema, host, porta, path, query e fragment di:
http://www.scuola.it:8080/orari/classe.php?sezione=5A#lunedi

Soluzione
  • schema: http
  • host: www.scuola.it
  • porta: 8080 (diversa da quella di default, quindi va scritta)
  • path: /orari/classe.php
  • query: sezione=5A
  • fragment: lunedi
02Porta sottintesa facile

A quale porta si collega il browser per https://www.example.com/? E per http://www.example.com/?

Soluzione

La porta non è scritta, quindi si usa quella di default: 443 per https e 80 per http.

03Scrivi la richiesta medio

Scrivi la request HTTP/1.1 che il browser invia per aprire http://www.istitutovolta.edu/informatica/home.html, accettando solo pagine HTML.

Soluzione
GET /informatica/home.html HTTP/1.1
Host: www.istitutovolta.edu
User-Agent: Mozilla/5.0
Accept: text/html

Nella riga di richiesta va solo il path; il nome del server va nell'header Host. Il messaggio finisce con una riga vuota e, con GET, non ha corpo.

04Leggi la risposta medio
HTTP/1.1 404 Not Found
Date: Mon, 06 Oct 2025 09:12:40 GMT
Server: nginx
Content-Type: text/html
Content-Length: 153
Connection: close

a) La richiesta è andata a buon fine? Di chi è l'errore?
b) Che cosa contiene il corpo?
c) Cosa succede alla connessione TCP?

Soluzione

a) No: 404 Not Found significa che la risorsa non esiste. Il codice inizia con 4, quindi l'errore è del client (ha chiesto un indirizzo sbagliato).
b) Una pagina HTML (text/html) di 153 byte, di solito la pagina di errore.
c) Connection: close: il server la chiude dopo la risposta.

05GET o POST? facile

Quale metodo useresti per: a) una ricerca su un motore di ricerca; b) il modulo di login; c) caricare una foto profilo?

Soluzione

a) GET: legge dati e l'URL della ricerca si può salvare o condividere.
b) POST: la password deve stare nel corpo, non nell'URL.
c) POST: invia dati (il file) al server.

06Quante connessioni? ragionamento

Una pagina è formata da un file HTML e 4 immagini. Quante connessioni TCP servono con HTTP/1.0? E con HTTP/1.1 persistente?

Soluzione

I file sono 1 + 4 = 5. Con HTTP/1.0 serve una connessione per ogni file: 5 connessioni, ognuna con la sua stretta di mano a 3 segmenti. Con HTTP/1.1 persistente basta 1 connessione per tutti e 5 i file.
