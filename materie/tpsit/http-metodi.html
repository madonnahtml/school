I metodi HTTP e le API REST

UD2, lezione 2: le caratteristiche dei metodi HTTP, le differenze tra GET e POST e come i metodi vengono usati dalle applicazioni (API RESTful) per creare, leggere, modificare e cancellare dati su un server.

Prima di iniziareCom'è fatta una richiesta (request line, header, body) è spiegato nel capitolo Il protocollo HTTP. Lo stesso argomento, visto dal libro di Sistemi e Reti, è in HTTP: i metodi (verbi).
Le 5 cose che contano
  1. Il metodo (o verbo) è la prima parola della richiesta: dice al server che cosa vuole fare il client.
  2. Le API RESTful usano quattro metodi per le operazioni CRUD: POST crea, GET legge, PUT modifica, DELETE cancella.
  3. GET mette i parametri nell'URL (query string, dopo il ?); POST li mette nel body.
  4. La codifica URL trasforma i caratteri "non sicuri" in %xx (spazio → %20).
  5. PUT è idempotente: ripeterla più volte lascia il server come dopo la prima volta. POST no.

Che cos'è un metodo HTTP

I metodi (chiamati anche verbi) sono attributi di una richiesta HTTP: esprimono l'intenzione del client. Alcuni si usano raramente, ma ognuno ha il suo scopo.

Il metodo è sempre la prima parola della prima riga di una request, ed è scritto in maiuscolo:

DELETE /prove/risorsa HTTP/1.1 
GET / HTTP/1.1                    ← chiede la pagina principale del sito
DELETE /prove/risorsa HTTP/1.1    ← chiede di cancellare /prove/risorsa
Il paragoneIl server è un magazzino e ogni risorsa è una scatola con la sua etichetta (l'URL). Il metodo è il verbo dell'ordine che dai al magazziniere: «prendi la scatola 3» (GET), «metti questa scatola al posto 3» (PUT), «ricevi questo pacco e sistemalo tu» (POST), «butta la scatola 3» (DELETE).

Le API e le applicazioni RESTful

Un'API (Application Programming Interface) è un insieme di regole, protocolli e strumenti che permette a utenti o ad altri programmi di comunicare e interagire con un sistema software.

Le API HTTP si raggiungono tramite URL precisi e usano i metodi GET, POST, PUT e DELETE per lavorare sulle risorse messe a disposizione dal server: si possono ottenere informazioni, modificarle, crearle o cancellarle.

REST e RESTfulREST significa REpresentational State Transfer. Le applicazioni RESTful permettono di fare operazioni da remoto sui dati presenti nei server (che lo consentono) usando proprio i metodi del protocollo HTTP.

Un sito web

Risponde con pagine HTML, pensate per essere lette da una persona nel browser.

Il menu illustrato appeso fuori dal ristorante.

Un'API

Risponde con dati puri, di solito in JSON, pensati per essere usati da un altro programma (per esempio l'app meteo del telefono).

Il cameriere: tu ordini con un formato preciso e ricevi il piatto, senza entrare in cucina.

Le regole di REST

  • Tutto è una risorsa, identificata da un URL: /users/3, /posts/1. L'URL contiene nomi, mai verbi: /posts/1 e non /cancellaPost?id=1.
  • Il metodo HTTP dice cosa fare sulla risorsa.
  • Il server non ricorda nulla tra una richiesta e l'altra (stateless): ogni richiesta porta con sé tutto ciò che serve.
  • Le risorse viaggiano in una rappresentazione, oggi quasi sempre JSON (vedi Le rappresentazioni HTTP).

Queste regole sono riprese dalla consegna dell'esercitazione Classroom Esercizi HTTP e Postman, dove si provano su un'API vera.

Le operazioni CRUD

Le operazioni di base sui dati si chiamano CRUD, dalle iniziali di Create, Retrieve, Update, Delete: crea, recupera, aggiorna e cancella. Ognuna corrisponde a un metodo HTTP.

Il metodo GET

Il metodo GET chiede una risorsa al server, ordinandogli di trasmettere al client le informazioni identificate dall'URL. È una richiesta di sola lettura: una volta ricevuti i dati, il client è libero di farci quello che vuole (per esempio formattarli per mostrarli).

GET /pathname HTTP/1.1

Il server manda l'oggetto richiesto nel body della risposta e indica il successo con il codice 200 nella status line. Se non può (o non vuole) mandarlo, risponde con un altro codice di stato.

  1. 1Client → serverGET URI: «mandami questa risorsa».
  2. 2Server → client200 OK + i dati nel body.

Esempio: request e response

Host: www.apollo.it                    ← header lines
Connection: close                      ← chiudi la connessione al termine della richiesta
User-agent: Chrome/37.0
Accept: text/html, image/gif
Accept-language: it
                                       ← il body è vuoto

Content-Type: text/html

<!DOCTYPE html>
<html>...</html>                       ← i dati: la pagina HTML richiesta

I parametri nella query string

GET permette di passare dei parametri nella sezione query dell'URL. La query string:

  • si trova dopo il punto interrogativo ?;
  • contiene una o più coppie chiave=valore;
  • le coppie sono separate dal carattere &.
https://www.dominio.com/prodotti?categoria=scarpe&prezzo=basso 
https://www.dominio.com/prodotti?categoria=scarpe&prezzo=basso
https://www.esempio.com/smartphone?brand=samsung&color=nero
Il limite di GETLa lunghezza massima di un URL è limitata (browser e server tagliano gli URL troppo lunghi), quindi con GET non si possono mandare grandi quantità di dati. E i parametri si vedono nella barra degli indirizzi e nella cronologia: mai metterci una password.

La codifica URL (URL encode)

L'URL encode è la procedura che prepara una stringa di dati, codificandola in modo che venga riconosciuta durante la trasmissione HTTP con GET o POST. Si usa nelle query string per mettere negli URL testi conformi allo standard degli URL, e per inviare i campi di un form HTML.

La stringa da inviare è una serie di coppie nome campo e valore: il nome campo è come una variabile, il valore è il dato che contiene.

Perché serveIn un URL alcuni caratteri hanno già un compito: ? apre la query, & separa i parametri, = separa nome e valore, # indica un punto della pagina. Se uno di questi caratteri fa parte del dato (per esempio "1+1=2"), il server si confonderebbe. La codifica li "traveste" in modo che non vengano scambiati per separatori.

I passaggi

  1. 1ConvertireOgni carattere non sicuro diventa %xx, dove xx è il suo codice ASCII in esadecimale. Sono non sicuri =, &, %, @, lo spazio, +, le lettere accentate, ?, # e i caratteri non stampabili.
  2. 2Eliminare gli spaziOgni spazio diventa %20.
  3. 3UnireNome e valore si uniscono con =; le coppie si separano con &: nome1=valore1&nome2=valore2&nome3=valore3.

Esempio

Vogliamo inviare con la query string la frase A scuola ho imparato che 1+1=2:

Testo:       A scuola ho imparato che 1+1=2
Codificato:  A%20scuola%20ho%20imparato%20che%201%2B1%3D2
Nell'URL:    pagina.php?stringa=A%20scuola%20ho%20imparato%20che%201%2B1%3D2

Gli spazi sono diventati %20, il + è diventato %2B e l'= è diventato %3D. L'unico = rimasto "vero" è quello tra il nome del parametro (stringa) e il suo valore. Questa codifica garantisce che l'URL sia valido e che il server lo interpreti correttamente.

Il metodo PUT

Il metodo PUT chiede di memorizzare sul server una risorsa all'URL indicato. Serve quindi a trasmettere informazioni dal client al server, come POST, ma con PUT si ha la creazione di una risorsa: l'argomento di PUT è proprio la risorsa che ci si aspetta di ottenere facendo, in seguito, una GET con lo stesso nome.

PUT /pathname HTTP/1.1

Il request body è:

  • una nuova risorsa da memorizzare sul server all'URI indicato (pathname), se lì non c'è ancora niente;
  • una nuova versione da sostituire a quella che c'è già a quell'URI.
  1. 1Client → serverPUT URI + i dati: «salva questo a questo indirizzo».
  2. 2Server → clientun codice di stato e, se vuole, dei dati (200 OK + data).

Esempio

PUT /avviso.txt HTTP/1.1
Host: scuolaonline.it
Content-Type: text/plain
Content-Length: 34

Il 12/3/2020 non ci sarà lezione.

Nelle slide la riga dell'host è scritta Host: scuolaonline.it 80 e la lunghezza è 80 byte: la forma corretta dell'header è Host: scuolaonline.it (oppure scuolaonline.it:80), e Content-Length deve contare i byte veri del body.

Le risposte possibili

CodiceQuando
201 CreatedLa risorsa non esisteva ed è stata creata.
200 OKLa risorsa esisteva ed è stata sostituita; la risposta contiene dei dati.
204 No ContentLa risorsa esisteva ed è stata sostituita; la risposta non ha body.

Il metodo POST

A differenza di GET, con POST i dettagli per identificare ed elaborare la risorsa non sono nell'URL, ma nel body del messaggio. POST si usa spesso per inviare i dati di un form HTML a un'applicazione sul server.

La trasmissione avviene come per PUT: il client manda un messaggio POST con l'informazione da inviare, il server risponde con un codice di stato (ed eventualmente dei dati).

POST si differenzia da GET perché

  • il client invia un blocco di dati nel corpo della request;
  • di solito ci sono degli header che descrivono il corpo, come Content-Type e Content-Length;
  • l'URI richiesto non è una risorsa da prelevare, ma un programma (un'API) che gestisce i dati ricevuti.

Considerazioni

  • Con POST non ci sono limiti di lunghezza dei parametri: i campi del form vanno nel body, non nell'URL.
  • POST non è sicuro di per sé: i dati non si vedono nell'URL, ma viaggiano comunque in chiaro. Per proteggerli serve HTTPS.

Esempio

POST /cgi-bin/rates.cgi HTTP/1.1                    ← metodo, programma (CGI) sul server, protocollo
Referer: http://nes:8192/cgi-bin/rats.cgi
Connection: Keep-Alive
User-Agent: Mozilla/4.73 [en] (X11; U; Linux 2.2.12-20 i686)
Host: nes:8192
Accept: image/gif, image/x-xbitmap, image/jpeg, image/pjpeg, image/png, */*
Accept-Encoding: gzip
Accept-Language: en
Accept-Charset: iso-8859-1,*,utf-8
Content-type: application/x-www-form-urlencoded      ← i dati sono in URL encode
Content-length: 93                                   ← lunghezza in byte dei campi

Account=cs111fall&First=richard&Last=martin&SSN=123456789&Bday=01011980&.State=CreateAccount

Il body contiene le stesse coppie nome=valore&… della query string, codificate in URL encode: è questo che dice application/x-www-form-urlencoded.

Le risposte del server a una POST

CodiceSignificato
200 OKI dati sono stati ricevuti e inviati alla risorsa, e il server restituisce una risposta al client.
201 CreatedI dati sono stati ricevuti, la risorsa non esisteva ed è stata creata.
204 No ContentI dati sono stati ricevuti e inviati alla risorsa, ma non viene restituita una risposta al client.

POST e PUT a confronto

POST

Serve a creare dati sul server. L'URI è il programma che li riceve: è il server a decidere dove metterli (e che id dargli).

Ripetere 3 volte la stessa POST può creare 3 risorse.

«Ecco una lettera, mettila tu nella casella giusta.»

PUT

Serve a modificare o sostituire dati sul server. L'URI è il nome della risorsa stessa: decide il client dove va.

Ripetere 3 volte la stessa PUT lascia una sola risorsa, sempre uguale.

«Metti questa lettera nella casella 12.»

IdempotenteUn metodo è idempotente se ripetere più volte la stessa richiesta produce sul server lo stesso effetto di farla una volta sola. PUT è idempotente; POST no. Anche GET (non cambia niente) e DELETE (dopo la prima volta la risorsa non c'è più) sono idempotenti.

Il metodo DELETE

Con DELETE si chiede l'eliminazione della risorsa all'URI indicato. Permette al client di rimuovere oggetti dal server da remoto: funziona al rovescio rispetto a PUT, perché la risorsa non viene salvata ma eliminata.

  1. 1Client → serverDELETE URI: il messaggio con l'URL della risorsa da rimuovere.
  2. 2Server → clientun codice di stato (200 OK + eventuali dati, oppure un errore).
AttenzioneNon c'è nessuna garanzia che la risorsa venga davvero cancellata, anche se il server risponde 200 OK: la risposta dice solo che il server ha accettato la richiesta.

Esempio: richiesta e risposte

Richiesta di cancellare il file file.txt nella root del server:

DELETE /file.txt HTTP/1.1
Host: www.scuolaonline.it

Il server può anche rispondere con un codice di errore, come in questo caso:

HTTP/1.1 405 Method Not Allowed
Date: Mon, 12 Nov 2024 17:45:11 GMT
Server: Apache/3.0.32 (UNIX) DAV 2
Allow: GET, HEAD, OPTIONS, TRACE         ← i metodi che invece sono permessi
Content-Type: text/html;

<HTML>
...
</HTML>

405 Method Not Allowed significa che su quella risorsa il metodo DELETE non è permesso (le slide dicono "richiesta non autorizzata"). L'header Allow elenca i metodi che si possono usare.

Mappa riassuntiva

  • I metodi HTTP sono presenti nelle request HTTP: GET, POST, PUT, HEAD, DELETE, OPTIONS, TRACE.
  • Le request inviano la query string, codificata mediante URL encode.
  • I metodi sono ammessi dalle API, che servono alle applicazioni RESTful (REpresentational State Transfer) per le operazioni CRUD: Create → POST, Retrieve → GET, Update → PUT, Delete → DELETE.
  • La richiesta GET può essere assoluta, parziale o condizionale; quella condizionale usa gli header If-Match, If-Modified-Since e If-Range («mandamela solo se…»).

Esercizi

01Quale metodo? facile

Per ogni operazione su un'API di una scuola scrivi metodo e URL: a) leggere lo studente 7; b) iscrivere un nuovo studente; c) sostituire i dati dello studente 7; d) cancellare lo studente 7; e) leggere tutti gli studenti della 5A.

Soluzione

a) GET /studenti/7
b) POST /studenti (con i dati nel body; l'id lo sceglie il server)
c) PUT /studenti/7 (con i dati completi nel body)
d) DELETE /studenti/7
e) GET /studenti?classe=5A (il filtro va nella query string)

02Codifica URL facile

Codifica in URL encode la query string con citta = Reggio Emilia, email = anna@scuola.it e voto = 7+.

Soluzione

?citta=Reggio%20Emilia&email=anna%40scuola.it&voto=7%2B

Spazio → %20, @ → %40, + → %2B. Il ? iniziale, gli = tra nome e valore e le & tra le coppie restano come sono, perché fanno da separatori.

03Decodifica medio

Che testo arriva al server con cerca.php?q=50%25%20di%20sconto%20%26%20spedizione? Perché il % e la & del testo sono stati codificati?

Soluzione

Il parametro q vale 50% di sconto & spedizione.

La & scritta così com'è avrebbe chiuso il parametro q e iniziato un nuovo parametro chiamato " spedizione". Il % scritto così com'è sarebbe stato letto come inizio di un codice %xx: per questo anche il % stesso va codificato, in %25.

04Scrivi la POST medio

Un form di iscrizione su www.palestra.it invia i campi nome = Luca Bianchi e corso = yoga al programma /iscrivi.php. Scrivi la request completa.

Soluzione
POST /iscrivi.php HTTP/1.1
Host: www.palestra.it
Content-Type: application/x-www-form-urlencoded
Content-Length: 30

nome=Luca%20Bianchi&corso=yoga

L'URI è il programma che riceve i dati; i campi vanno nel body in URL encode. Content-Length conta i caratteri del body: nome=Luca%20Bianchi (19) + & (1) + corso=yoga (10) = 30.

05Leggi la risposta medio
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD, OPTIONS

Il client aveva mandato PUT /listino.pdf. Che cosa è successo? Che metodo potrebbe usare per scaricare il file?

Soluzione

Il server non permette PUT su quella risorsa, quindi il file non è stato caricato né sostituito. L'header Allow dice che sono ammessi solo GET, HEAD e OPTIONS: per scaricare il file si usa GET.

06Idempotenza ragionamento

Per un errore di rete il browser rimanda 3 volte la stessa richiesta. Che cosa succede sul server se la richiesta era a) POST /ordini; b) PUT /profilo/12; c) DELETE /carrello/5?

Soluzione

a) POST non è idempotente: possono nascere 3 ordini uguali (per questo i siti dicono «non premere due volte il tasto Paga»).
b) PUT è idempotente: il profilo 12 viene sostituito 3 volte con gli stessi dati, il risultato finale è identico.
c) DELETE è idempotente: la prima volta il prodotto 5 sparisce dal carrello, le altre due non c'è più niente da cancellare. Lo stato del server è lo stesso, anche se le risposte successive potrebbero essere diverse (per esempio 404).
