Classroom: HTTP e Postman (Parte 1)

L'esercitazione "Esercizi HTTP e Postman – Parte 1" assegnata su Google Classroom: nove esercizi in cui si mandano richieste HTTP vere con Postman e si leggono le risposte del server. Qui trovi la consegna riportata fedelmente, la risposta e la spiegazione di ogni punto. La teoria è nei capitoli I metodi HTTP e le API REST e I codici di stato e HTTPS.

Come usare questa paginaLeggi la consegna (è quella del PDF del professore), fai la richiesta in Postman e annota tu il risultato; solo dopo apri la risposta spiegata e confronta. Le risposte (status code, header e JSON) sono state ottenute mandando le stesse richieste al codice ufficiale di JSONPlaceholder e di httpbin, con gli stessi dati dei siti: sono quelle che ricevi anche tu.
Cosa può cambiare da teIl tempo di risposta, la dimensione mostrata da Postman, la versione di Postman nello User-Agent e alcuni header (data, Postman-Token…) dipendono dal tuo computer e dalla rete: i tuoi numeri saranno diversi. Status code e JSON invece devono essere uguali.

La consegna e il setup

Consegna. Usare Postman per inviare richieste HTTP reali e leggere le risposte del server. Per ogni esercizio annota in un file di testo la richiesta inviata, lo status code ricevuto e la risposta alla richiesta.

Obiettivi

  • Leggere e costruire una richiesta HTTP: metodo, URL, header, body.
  • Interpretare una risposta: status code, header, corpo JSON.
  • Usare i metodi CRUD (GET, POST, PUT, DELETE) su una API REST.

Prerequisiti: modello client-server, modello TCP/IP, formato JSON, concetto di URL.

Dove si trova cosa in Postman
  • In alto: il menu a tendina del metodo (GET, POST…), la barra dell'URL e il tasto Send.
  • Sotto l'URL, le schede della richiesta: Params (query string), Headers, Body.

Cos'è una API REST

Dalla consegna. Una API (Application Programming Interface) è un servizio pensato per essere usato da altri programmi, non da persone: risponde con dati puri, di solito in JSON, invece che con pagine HTML. L'app meteo del telefono, per esempio, non legge il sito web ma interroga un'API.

Pensa a un cameriere al ristorante: il cliente (client) non entra in cucina (server e database), ordina dal menu (la documentazione dell'API) con un formato preciso e riceve il piatto (la risposta). La cucina può riorganizzarsi senza che il cliente se ne accorga.

REST è un insieme di regole per costruire API sopra HTTP:

  • Tutto è una risorsa, identificata da un URL: /users/3, /posts/1. L'URL contiene nomi, mai verbi: /posts/1 e non /cancellaPost?id=1.
  • Il metodo HTTP dice cosa fare sulla risorsa.
  • Il server non ricorda nulla tra una richiesta e l'altra (stateless): ogni richiesta porta con sé tutto ciò che serve, compresa l'autenticazione.
  • Le risorse viaggiano in una rappresentazione, oggi quasi sempre JSON.
Operazione (CRUD)Metodo HTTPEquivalente SQLEsempioRisposta tipica
CreatePOSTINSERTPOST /posts201 Created
ReadGETSELECTGET /posts/1200 OK
UpdatePUT / PATCHUPDATEPATCH /posts/1200 OK
DeleteDELETEDELETEDELETE /posts/1200 o 204

Prova subito: apri nel browser https://jsonplaceholder.typicode.com/users/1, poi /users/1/posts. Un'API è solo un URL che restituisce JSON. Il browser però sa inviare solo GET: per usare tutti i metodi serve Postman.

Attenzione a tre errori comuni:

  • API e REST non sono sinonimi: REST è uno stile, ed esistono API non REST (SOAP, GraphQL, gRPC).
  • REST non obbliga a usare JSON: è solo la rappresentazione più diffusa.
  • Un URL come /getUsers è progettato male: il verbo lo dà il metodo HTTP.
★Per riflettere: l'API della biblioteca ragionamento

Consegna. Progetta URL e metodi per l'API di una biblioteca che permetta di elencare i libri, vederne uno, prestarlo e restituirlo. Suggerimento: anche il prestito può essere una risorsa.

Risposta spiegata

Ragionamento

Le prime due operazioni sono letture sulla risorsa libri. Per "prestare" non invento un URL con un verbo come /prestaLibro: seguo il suggerimento e tratto il prestito come una risorsa a sé, che si crea, si legge e si modifica.

OperazioneMetodoURLBodyRisposta
Elencare i libriGET/libri–200 + array di libri
Vedere un libroGET/libri/12–200 (o 404 se non esiste)
Prestare un libroPOST/prestiti{ "libroId": 12, "utenteId": 5 }201 + il prestito con il suo id
RestituirloPATCH/prestiti/7{ "restituito": true }200

Per la restituzione si poteva usare anche DELETE /prestiti/7: però così il prestito sparisce e la biblioteca perde lo storico. Con PATCH il prestito resta, segnato come chiuso. Con lo stesso schema si aggiungono GET /prestiti?utenteId=5 (i prestiti di un utente) o GET /libri?autore=Manzoni (filtri nella query string).

Livello base – Richieste GET e lettura della risposta

01La prima richiesta facile

Obiettivo: riconoscere le parti di una risposta HTTP · Difficoltà: bassa · Tempo: 10 min

Consegna. Invia una richiesta GET https://jsonplaceholder.typicode.com/posts/1.

  1. Qual è lo status code? Cosa significa?
  2. Nella scheda Headers della risposta, qual è il valore di Content-Type?
  3. Quali campi contiene l'oggetto JSON restituito?
  4. Quanto tempo ha impiegato la risposta e quanto pesa (in byte)?
Risposta spiegata

La risposta del server

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 292
{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit",
  "body": "quia et suscipit\nsuscipit recusandae consequuntur expedita et cum\nreprehenderit molestiae ut ut quas totam\nnostrum rerum est autem sunt rem eveniet architecto"
}
  1. 200 OK: la richiesta è andata a buon fine e il server ha mandato la risorsa nel body. È della classe 2xx (successo).
  2. Content-Type: application/json; charset=utf-8: il body è in formato JSON, con i caratteri codificati in UTF-8.
  3. Quattro campi: userId (numero, l'autore del post), id (numero, l'identificativo del post), title (stringa) e body (stringa). Il testo è in finto latino ("lorem ipsum"): sono dati di prova.
  4. Si legge in alto a destra nella risposta: Time (per esempio un centinaio di millisecondi) e Size. Il body pesa 292 byte (lo dice anche l'header Content-Length); la Size di Postman è più grande (circa 1 KB o più) perché conta anche gli header della risposta. Il tempo cambia a ogni invio, perché dipende dalla rete.

Errori da evitare

  • Confondere la scheda Headers della richiesta (sotto l'URL) con quella della risposta (in basso): Content-Type va letto in basso.
  • Scrivere "il body è un oggetto" senza dire quali sono i campi: la domanda li chiede tutti e quattro.
02Collezioni e risorse annidate facile

Obiettivo: capire la struttura degli URL REST · Difficoltà: bassa · Tempo: 10 min

  1. Invia GET /posts. Quanti post vengono restituiti? Che tipo di dato JSON è la risposta (oggetto o array)?
  2. Invia GET /posts/1/comments. Quanti commenti ha il post 1?
  3. Invia GET /users/3. Qual è il nome dell'utente e in che città abita?
Risposta spiegata

  2. 5 commenti. /posts/1/comments è una risorsa annidata: "i commenti del post 1". Ogni commento ha postId, id, name, email e body.
  3. L'utente 3 si chiama Clementine Bauch (username Samantha) e abita a McKenziehaven. La città non è un campo "in superficie": si trova dentro l'oggetto annidato address, cioè in address.city.

  1. Invia GET /posts/999. Che status code ottieni? Che cosa contiene il body?
  2. Usando httpbin, invia GET https://httpbin.org/status/200, poi /status/404, /status/500, /status/301.
  3. Completa la tabella:
CodiceClasse (1xx–5xx)SignificatoDi chi è la "colpa": client o server?

Risposta spiegata
  1. 404 Not Found: i post sono solo 100, il 999 non esiste. Il body è un oggetto JSON vuoto: {}.
  2. httpbin risponde con il codice che gli chiedi e con il body vuoto: /status/200 → 200 OK, /status/404 → 404 Not Found, /status/500 → 500 Internal Server Error.
    Con /status/301 c'è una sorpresa: Postman mostra 200 OK e un JSON. Il server ha risposto 301 Moved Permanently con l'header Location: /redirect/1, e Postman ha seguito il reindirizzamento da solo (prima /redirect/1, poi /get), come fa un browser. Per vedere il 301 vero, nella scheda Settings della richiesta disattiva Automatically follow redirects e reinvia.

04Query string e filtri medio

Obiettivo: usare i parametri nell'URL · Difficoltà: media · Tempo: 15 min

  1. Usando la scheda Params di Postman (non scrivendo a mano nell'URL), recupera tutti i todo dell'utente 1: GET /todos con parametro userId = 1. Copia l'URL completo che Postman ha generato.
  2. Aggiungi un secondo parametro per ottenere solo i todo completati dell'utente 1. Quanti sono?
  3. Spiega a cosa servono i caratteri ? e & nell'URL.
Risposta spiegata
  1. Nella scheda Params scrivo Key userId e Value 1; Postman aggiorna l'URL da solo: 
    https://jsonplaceholder.typicode.com/todos?userId=1
    Risposta 200 OK con un array di 20 todo (id da 1 a 20).
  2. Aggiungo una seconda riga: Key completed, Value true. 
    https://jsonplaceholder.typicode.com/todos?userId=1&completed=true
    I todo completati dell'utente 1 sono 11 (quelli con id 4, 8, 10, 11, 12, 14, 15, 16, 17, 19, 20).
  3. ? separa il percorso della risorsa (/todos) dalla query string, cioè i parametri. & separa un parametro nome=valore dal successivo. Qui servono come filtri: chiedo sempre la collezione /todos, ma solo gli elementi che rispettano le condizioni (come un WHERE in SQL).

Errori da evitare

  • Scrivere userid con la i minuscola: il nome del campo è userId, e con il nome sbagliato il filtro viene ignorato o non trova niente.
  • Mettere un secondo ? al posto della &: il ? va scritto una volta sola.
05Gli header della richiesta medio

Obiettivo: capire che anche il client invia header · Difficoltà: media · Tempo: 10 min

  1. Invia GET https://httpbin.org/headers. httpbin ti restituisce gli header che tu hai inviato. Quale User-Agent usa Postman?
  2. Aggiungi nella scheda Headers un header personalizzato X-Classe con valore 5A (o la tua classe) e reinvia. Verifica che compaia nella risposta.
  3. Aggiungi l'header Accept-Language: it-IT. A cosa serve questo header in un sito reale?
Risposta spiegata

Dopo aver aggiunto i due header, la risposta (200 OK) è simile a questa:

{
  "headers": {
    "Accept": "*/*",
    "Accept-Encoding": "gzip, deflate, br",
    "Accept-Language": "it-IT",
    "Cache-Control": "no-cache",
    "Host": "httpbin.org",
    "Postman-Token": "1b2c3d4e-…",
    "User-Agent": "PostmanRuntime/7.43.0",
    "X-Amzn-Trace-Id": "Root=1-…",
    "X-Classe": "5A"
  }
}
  1. Postman si presenta come PostmanRuntime/7.x.x (il numero dipende dalla versione installata). Un browser invece manderebbe qualcosa come Mozilla/5.0 (Windows NT 10.0; …) Chrome/…. Lo User-Agent dice al server che programma sta facendo la richiesta.
  2. Nella risposta compare "X-Classe": "5A": il server ha ricevuto davvero l'header che ho aggiunto. Gli header che iniziano con X- sono per tradizione quelli personalizzati, non standard. X-Amzn-Trace-Id invece non l'ho mandato io: lo aggiunge il sistema (di Amazon) che sta davanti a httpbin.
  3. Accept-Language dice al server in che lingua l'utente preferisce i contenuti. Un sito multilingua lo legge e risponde con la versione italiana della pagina (il browser lo imposta da solo in base alla lingua del sistema). httpbin non ha pagine in più lingue, quindi si limita a restituirlo.

Gli header che non hai scritto tu (Accept, Accept-Encoding, Cache-Control, Postman-Token…) li aggiunge Postman in automatico: li vedi nella scheda Headers cliccando su hidden.

06Creare una risorsa con POST medio

Obiettivo: inviare un body JSON · Difficoltà: media · Tempo: 15 min

Consegna. Invia POST https://jsonplaceholder.typicode.com/posts con questo body (scheda Body → raw → JSON):

{
  "title": "Il mio primo post",
  "body": "Scritto con Postman in laboratorio",
  "userId": 1
}
  1. Qual è lo status code? Perché è diverso da quello di una GET riuscita?
  2. Che id ha assegnato il server alla nuova risorsa?
  3. Controlla la scheda Headers della richiesta: che valore ha impostato Postman per Content-Type?
  4. Ripeti la richiesta scegliendo Body → raw → Text invece di JSON. Cosa cambia nella risposta? Perché?
Risposta spiegata

La risposta

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
{
  "title": "Il mio primo post",
  "body": "Scritto con Postman in laboratorio",
  "userId": 1,
  "id": 101
}
  1. 201 Created. Una GET riuscita risponde 200 OK perché legge una risorsa che esiste già; la POST invece ha creato una risorsa nuova, e il codice più preciso per dirlo è 201.
  2. "id": 101. Con POST è il server a scegliere l'id: i post sono 100, quindi il prossimo è 101. Se rileggi GET /posts/101 ottieni 404: il salvataggio era solo simulato.
  3. Content-Type: application/json. Scegliendo "JSON" nel menu del body, Postman aggiunge da solo questo header, così il server sa che il body è JSON.
  4. Con Text Postman manda Content-Type: text/plain. Lo status resta 201, ma la risposta diventa solo: 
    {
  "id": 101
}
    Il testo inviato è identico, ma il server guarda il Content-Type per capire come leggere il body: con text/plain non lo interpreta come JSON, quindi non trova i campi title, body e userId e crea una risorsa che ha solo l'id. È la prova che l'header Content-Type fa parte della rappresentazione della risorsa.
07PUT e PATCH a confronto medio

Obiettivo: distinguere sostituzione completa e modifica parziale · Difficoltà: media · Tempo: 15 min

  1. Invia PUT /posts/1 con body { "title": "Titolo nuovo" }. Quali campi contiene la risposta?
  2. Invia PATCH /posts/1 con lo stesso body. Quali campi contiene ora la risposta?
  3. Spiega con parole tue la differenza tra PUT e PATCH, usando le due risposte come prova.
Risposta spiegata
  1. Risposta 200 OK con solo due campi, title e id: 
    {
  "title": "Titolo nuovo",
  "id": 1
}
  2. Risposta 200 OK con tutti e quattro i campi; è cambiato solo title: 
    {
  "userId": 1,
  "id": 1,
  "title": "Titolo nuovo",
  "body": "quia et suscipit\nsuscipit recusandae consequuntur expedita et cum\nreprehenderit molestiae ut ut quas totam\nnostrum rerum est autem sunt rem eveniet architecto"
}
  3. PUT sostituisce tutta la risorsa con quello che mando: avendo mandato solo il titolo, il post "nuovo" ha solo il titolo (più l'id, che viene dall'URL), e userId e body sono spariti. PATCH modifica solo i campi che mando e lascia gli altri come erano. Quindi: con PUT devo mandare la risorsa completa; con PATCH basta la parte da cambiare.

Paragone: PUT è ristampare tutta la scheda dello studente partendo da un foglio bianco; PATCH è correggere una sola riga con il bianchetto.

08Cancellare una risorsa medio

Obiettivo: usare DELETE e verificare l'idempotenza · Difficoltà: media · Tempo: 10 min

  1. Invia DELETE /posts/1. Che status code e che body ricevi?
  2. Invia di nuovo la stessa richiesta. Il risultato cambia?
  3. Un metodo si dice idempotente se ripeterlo più volte produce lo stesso effetto sul server di una volta sola. Quali tra GET, POST, PUT, PATCH, DELETE sono idempotenti? Motiva.
Risposta spiegata
  1. 200 OK con body {} (oggetto vuoto): la cancellazione è riuscita e non c'è più niente da mostrare.
  2. No: di nuovo 200 OK e {}. Su JSONPlaceholder la cancellazione è finta (con GET /posts/1 il post c'è ancora), quindi ogni volta "cancella" con successo. Su un server vero la seconda DELETE risponderebbe probabilmente 404, perché il post non c'è più: la risposta cambia, ma lo stato del server no (il post è cancellato in entrambi i casi).
    • GET: sì. Legge e basta, non cambia niente, quante volte la ripeti.
    • POST: no. Ogni POST crea una risorsa nuova: tre POST uguali = tre post (con id diversi).
    • PUT: sì. Mette la stessa risorsa allo stesso URL: dopo la prima volta, le altre la sostituiscono con una copia identica.
    • DELETE: sì. Dopo la prima volta la risorsa non c'è più, e le altre non cambiano niente.
    • PATCH: non è garantito. { "title": "Titolo nuovo" } ripetuto dà sempre lo stesso risultato, ma una PATCH come «aumenta i like di 1» cambierebbe il risultato a ogni invio. Per questo PATCH, in generale, non è considerato idempotente.
09Progettare le richieste medio

Obiettivo: tradurre un requisito in una richiesta REST · Difficoltà: media · Tempo: 15 min

Consegna. Completa la tabella scrivendo metodo, URL e (se serve) body. Poi prova ogni richiesta in Postman e annota lo status code.

Risposta spiegata

Tutti gli URL iniziano con https://jsonplaceholder.typicode.com.

OperazioneMetodoURLBodyStatus
Album dell'utente 2GET/users/2/albums
(oppure /albums?userId=2)		–200 (10 album)

Perché queste scelte

  • Leggere = GET, senza body. "Gli album dell'utente 2" si scrive come risorsa annidata (/users/2/albums) o come filtro nella query string (?userId=2): JSONPlaceholder accetta entrambe le forme e dà lo stesso risultato.
  • Creare = POST sulla collezione /todos, senza id (lo assegna il server: i todo sono 200, quindi 201). completed è un booleano: si scrive false senza virgolette.
  • "Senza toccare gli altri campi" è l'indizio per PATCH: con PUT e solo completed, il todo perderebbe titolo e utente (come nell'esercizio 7). La risposta è il todo intero con "completed": true: 
    {
  "userId": 1,
  "id": 7,
  "title": "illo expedita consequatur quia in",
  "completed": true
}
  • Eliminare = DELETE sull'URL del singolo commento, senza body.

Ricorda di selezionare Body → raw → JSON per POST e PATCH, altrimenti succede come nell'esercizio 6 con il Text.
