L'esercitazione pratica assegnata su Classroom, Esercitazione pratica Java – Eccezioni e gestione dei file: un programma RegistroStudenti a menu, robusto agli errori, che salva i nomi in un file. Consegna riportata fedelmente, con risposta e spiegazione punto per punto. La teoria è nei capitoli Java: eccezioni e Java: gestione dei file.

Come usare questa paginaI punti da 1 a 8 sono i pezzi del programma: per ognuno trovi la consegna del PDF, il codice che la realizza (preso dal programma finale) e la spiegazione. Prova a scrivere ogni pezzo da solo prima di aprire la risposta. 1. Struttura del menu

Ripasso lampoInteger.parseInt("abc") non può convertire il testo e lancia una NumberFormatException: se la catturi con catch il programma non si ferma. Teoria: try, catch e finally.
01Struttura del menu medio

Consegna. Il programma deve mostrare continuamente questo menu:

===== REGISTRO STUDENTI =====
1. Inserisci studente
2. Visualizza studenti
3. Cancella registro
4. Esci
=============================
Scelta:

La scelta deve essere letta tramite scanner.nextLine() e convertita in intero con Integer.parseInt(...).

Se l'utente inserisce qualcosa che non è un numero, il programma deve intercettare la NumberFormatException e mostrare:

Devi inserire un numero.

Il menu deve continuare a essere visualizzato.

Risposta spiegata

Ragionamento

  1. "Mostrare continuamente" vuol dire un ciclo: while (continua), con una variabile boolean che diventa false solo quando l'utente sceglie 4.
  2. Il menu lo metto in un metodo stampaMenu(): il main resta corto e leggibile. L'ultima riga usa print (non println), così l'utente scrive sulla stessa riga di Scelta:.
  3. Leggo la riga intera con nextLine() e la converto con Integer.parseInt. Se dentro c'è abc, parseInt lancia NumberFormatException, il switch viene saltato e si va dritti al catch.
  4. Il try-catch è dentro il ciclo: dopo il catch il ciclo riparte e il menu ricompare. Se fosse fuori dal ciclo, al primo errore il programma uscirebbe dal while.
  5. Un numero fuori dal menu (per esempio 7) non è un'eccezione: lo gestisce il default dello switch.

Codice

public static void main(String[] args) {
    boolean continua = true;

    while (continua) {
        stampaMenu();
        try {
            String riga = scanner.nextLine();
            System.out.println();
            int scelta = Integer.parseInt(riga.trim());   // può lanciare NumberFormatException

            switch (scelta) {
                case 1:
                    inserisciStudente();
                    break;
                case 2:
                    visualizzaStudenti();
                    break;
                case 3:
                    cancellaRegistro();
                    break;
                case 4:
                    System.out.println("Programma terminato.");
                    continua = false;
                    break;
                default:
                    System.out.println("Scelta non valida: scegli un numero da 1 a 4.");
            }
        } catch (NumberFormatException e) {
            // catch specifico: l'utente non ha scritto un numero
            System.out.println("Devi inserire un numero.");
        } catch (Exception e) {
            // catch generico: qualsiasi altro errore imprevisto
            System.out.println("Errore imprevisto: " + e.getMessage());
        }

        if (continua) {
            System.out.println();   // riga vuota prima del menu successivo
        }
    }
    scanner.close();
}

static void stampaMenu() {
    System.out.println("===== REGISTRO STUDENTI =====");
    System.out.println("1. Inserisci studente");
    System.out.println("2. Visualizza studenti");
    System.out.println("3. Cancella registro");
    System.out.println("4. Esci");
    System.out.println("=============================");
    System.out.print("Scelta: ");
}

Output (pezzo della sessione vera)

Scelta: abc

Devi inserire un numero.

===== REGISTRO STUDENTI =====
1. Inserisci studente
2. Visualizza studenti
3. Cancella registro
4. Esci
=============================
Scelta: 7

Scelta non valida: scegli un numero da 1 a 4.

Perché funziona

  • scanner è un attributo static della classe (static Scanner scanner = new Scanner(System.in);), così lo usano sia il main sia i metodi come inserisciStudente(), senza crearne uno nuovo ogni volta.
  • trim() toglie gli spazi prima e dopo: senza, un innocuo " 1" farebbe scattare NumberFormatException.
  • Perché nextLine() e non nextInt()? Con nextInt() l'invio rimane nel buffer e il successivo nextLine() (quello del nome) leggerebbe una riga vuota. Leggendo sempre righe intere il problema non esiste.
  • Il secondo catch (Exception e) è il punto 8 della consegna: lo vediamo lì.

2. Inserimento di uno studente

Ripasso lampoScrivere in append vuol dire aggiungere in fondo al file senza cancellare quello che c'è. Con FileWriter si passava true; con Files si passa StandardOpenOption.APPEND. Teoria: Scrivere in un file con FileWriter.
02Inserimento di uno studente medio

Consegna. Quando l'utente sceglie 1, chiedi:

Inserisci il nome dello studente:

Il nome deve essere aggiunto al file studenti.txt.

Utilizza Path e Files.writeString() con StandardOpenOption.APPEND.

Ogni studente deve essere scritto su una nuova riga.

Esempio di file:

Mario Rossi
Luca Bianchi
Anna Verdi

Gestione dell'errore. L'operazione sul file deve essere inserita in un try-catch per gestire eventuali errori di tipo IOException.

In caso di errore, visualizza un messaggio comprensibile all'utente.

Risposta spiegata

Ragionamento

  1. Il file lo indico una volta sola, come costante della classe: static final Path FILE = Path.of("studenti.txt");. È un percorso relativo: il file nasce nella cartella da cui parte il programma.
  2. Files.writeString(file, testo, opzioni...) scrive una stringa nel file. Per andare a capo aggiungo System.lineSeparator() dopo il nome (su Linux e Mac è \n, su Windows \r\n).
  3. Le opzioni sono due: APPEND (scrivi in fondo) e CREATE (crea il file se non c'è). Il PDF nomina solo APPEND, ma da solo non basta: vedi "Errori da evitare".
  4. writeString può lanciare IOException (disco pieno, permessi, ...): la catturo e stampo un messaggio in italiano, non lo stack trace.
  5. Prima di scrivere controllo il nome con controllaNome (punto 5), e alla fine un finally stampa "Operazione terminata." (punto 7).

Codice

static final Path FILE = Path.of("studenti.txt");

static void inserisciStudente() {
    System.out.print("Inserisci il nome dello studente: ");
    String nome = scanner.nextLine().trim();
    try {
        controllaNome(nome);
        Files.writeString(FILE, nome + System.lineSeparator(),
                StandardOpenOption.CREATE, StandardOpenOption.APPEND);
        System.out.println("Studente inserito.");
    } catch (IllegalArgumentException e) {
        System.out.println(e.getMessage());
    } catch (IOException e) {
        System.out.println("Impossibile salvare lo studente nel registro.");
    } finally {
        System.out.println("Operazione terminata.");
    }
}

Output

Ho eseguito il programma due volte di seguito senza cancellare il file: la prima volta ho inserito Mario Rossi, la seconda Luca Bianchi. Ecco studenti.txt alla fine:

Mario Rossi
Luca Bianchi

Mario è ancora lì: è proprio l'effetto di APPEND. Senza, ogni esecuzione cancellerebbe il registro precedente.

Per vedere il catch (IOException e) in azione ho creato apposta una cartella chiamata studenti.txt (in una cartella non si può scrivere testo). Risultato vero:

Scelta: 1

Inserisci il nome dello studente: Mario Rossi
Impossibile salvare lo studente nel registro.
Operazione terminata.

Errori da evitare

  • Solo APPEND, senza CREATE. Se il file non esiste ancora, Java non lo crea e lancia un'eccezione. Prova vera con Files.writeString(file, "Mario Rossi" + System.lineSeparator(), StandardOpenOption.APPEND) e nessun file presente: 
    Errore: java.nio.file.NoSuchFileException: studenti.txt
    Al primissimo inserimento il registro non esiste mai, quindi serve CREATE, APPEND.
  • Nessuna opzione. Files.writeString(FILE, testo) senza opzioni crea il file ma, se c'è già, lo svuota e riscrive: ogni studente cancellerebbe quello prima.
  • Dimenticare l'a capo. Senza System.lineSeparator() i nomi finiscono tutti attaccati sulla stessa riga: Mario RossiLuca Bianchi.

3. Visualizzazione degli studenti

Ripasso lampoPrima di leggere un file conviene controllare che esista: con File era f.exists(), con Files è Files.exists(path). Teoria: Verificare se un file esiste.
03Visualizzazione degli studenti medio

Consegna. Quando l'utente sceglie 2, il programma deve leggere tutte le righe del file studenti.txt.

Utilizza Files.readAllLines(...) e stampa gli studenti numerandoli:

===== STUDENTI =====
1. Mario Rossi
2. Luca Bianchi
3. Anna Verdi

Prima di leggere il file, controlla se esiste utilizzando Files.exists(...).

Se il file non esiste, visualizza:

Il registro non esiste ancora.

Anche questa operazione deve avere una propria gestione delle eccezioni.

Risposta spiegata

Ragionamento

  1. Primo controllo: if (!Files.exists(FILE)) → messaggio e basta. Il ! significa "non esiste".
  2. Altrimenti leggo: Files.readAllLines restituisce una List<String>, una stringa per ogni riga del file, già senza l'a capo.
  3. Per numerare scorro la lista con un for classico: la posizione i parte da 0, ma a schermo stampo i + 1. Attenzione alle parentesi: (i + 1) + ". ", altrimenti Java concatenerebbe "0" e "1" come testo.
  4. La lettura vera la fa il metodo leggiStudenti() (punto 6), che dichiara throws IOException: qui la gestisco con try-catch, come chiede la consegna.
  5. Caso in più: il file esiste ma è vuoto. Stampo "Il registro è vuoto." invece della sola intestazione.

Codice

static void visualizzaStudenti() {
    try {
        if (!Files.exists(FILE)) {
            System.out.println("Il registro non esiste ancora.");
        } else {
            List<String> studenti = leggiStudenti();
            if (studenti.isEmpty()) {
                System.out.println("Il registro è vuoto.");
            } else {
                System.out.println("===== STUDENTI =====");
                for (int i = 0; i < studenti.size(); i++) {
                    System.out.println((i + 1) + ". " + studenti.get(i));
                }
            }
        }
    } catch (IOException e) {
        System.out.println("Impossibile leggere il registro.");
    } finally {
        System.out.println("Operazione terminata.");
    }
}

Output (pezzi delle sessioni vere)

Con il file che non esiste ancora (prima scelta di un programma appena avviato):

Scelta: 2

Il registro non esiste ancora.
Operazione terminata.

Dopo aver inserito due studenti:

Scelta: 2

===== STUDENTI =====
1. Mario Rossi
2. Luca Bianchi
Operazione terminata.

E con la cartella al posto del file (il trucco del punto 2): Files.exists risponde true, ma readAllLines fallisce e scatta il catch:

Scelta: 2

Impossibile leggere il registro.
Operazione terminata.

Perché funziona

Files.exists evita l'errore più comune (il file non c'è) con un semplice if, senza passare da un'eccezione. Il try-catch resta comunque necessario per gli errori che nessun if può prevedere, come l'ultimo caso, e perché IOException è checked: senza catch il programma non compilerebbe.

4. Cancellazione del registro

Ripasso lampoFiles.deleteIfExists(path) elimina il file se c'è e restituisce true; se non c'è non fa nulla e restituisce false. È il fratello di f.delete() visto in Eliminare un file con delete.
04Cancellazione del registro facile

Consegna. Quando l'utente sceglie 3, il programma deve eliminare il file utilizzando Files.deleteIfExists(...).

Se il file viene eliminato:

Registro cancellato.

Se il file non esiste:

Il registro non esiste.

Eventuali errori di I/O devono essere gestiti tramite try-catch.

Risposta spiegata

Ragionamento

  1. Non serve chiamare prima Files.exists: il valore restituito da deleteIfExists mi dice già come è andata. Lo metto direttamente nell'if.
  2. deleteIfExists può lanciare IOException (per esempio file protetto o cartella non vuota): try-catch obbligatorio.

Codice

static void cancellaRegistro() {
    try {
        if (Files.deleteIfExists(FILE)) {
            System.out.println("Registro cancellato.");
        } else {
            System.out.println("Il registro non esiste.");
        }
    } catch (IOException e) {
        System.out.println("Impossibile cancellare il registro.");
    } finally {
        System.out.println("Operazione terminata.");
    }
}

Output (pezzi delle sessioni vere)

Scelta: 3

Registro cancellato.
Operazione terminata.
Scelta: 3

Il registro non esiste.
Operazione terminata.

Errori da evitare

Non confondere Files.deleteIfExists con Files.delete: quest'ultimo, se il file non c'è, lancia NoSuchFileException invece di restituire false. Con delete il messaggio "Il registro non esiste." andrebbe scritto in un catch, che è meno chiaro.

5. Utilizzo di throw

Ripasso lampothrow lancia tu un'eccezione quando un dato non va bene: throw new IllegalArgumentException("messaggio");. Teoria: throw e throws.
05Utilizzo di throw facile

Consegna. Crea un metodo controllaNome(String nome).

Il metodo deve controllare che il nome non sia vuoto.

Se l'utente non inserisce alcun nome, deve essere generata esplicitamente un'eccezione: throw new IllegalArgumentException(...)

Il messaggio deve essere:

Il nome non può essere vuoto.

Il catch dovrà intercettare l'eccezione e permettere al programma di continuare normalmente.

Risposta spiegata

Ragionamento

  1. "Vuoto" per me vuol dire anche "solo spazi": per questo controllo nome.trim().isEmpty() e non solo nome.isEmpty().
  2. Se il nome non va, throw crea l'eccezione con il messaggio richiesto e il metodo si interrompe subito: la riga dopo (la scrittura sul file in inserisciStudente) non viene eseguita.
  3. Il catch (IllegalArgumentException e) in inserisciStudente stampa e.getMessage(), cioè proprio il testo passato al costruttore. Poi il ciclo del menu continua.
  4. Questa è la "seconda eccezione" chiesta dalla consegna, oltre a NumberFormatException (e c'è anche IOException).

Codice

// Punto 5: throw. Se il nome è vuoto lancio io l'eccezione.
static void controllaNome(String nome) {
    if (nome == null || nome.trim().isEmpty()) {
        throw new IllegalArgumentException("Il nome non può essere vuoto.");
    }
}

// dentro inserisciStudente():
try {
    controllaNome(nome);
    Files.writeString(...);          // non arriva qui se il nome è vuoto
    System.out.println("Studente inserito.");
} catch (IllegalArgumentException e) {
    System.out.println(e.getMessage());
} ...

Output (pezzo della sessione vera, l'utente preme solo Invio)

Scelta: 1

Inserisci il nome dello studente:
Il nome non può essere vuoto.
Operazione terminata.

Perché funziona

IllegalArgumentException è unchecked (figlia di RuntimeException): per questo controllaNome non ha bisogno di throws nella firma. Il file non viene toccato e, controllando dopo con la voce 2, il nome vuoto non compare.

6. Utilizzo di throws

Ripasso lampothrows nella firma dichiara che il metodo può lanciare un'eccezione e che non la gestisce lui: la passa a chi lo chiama. Teoria: Checked e unchecked exceptions.
06Utilizzo di throws medio

Consegna. Crea un metodo separato leggiStudenti() che si occupi della lettura del file.

Il metodo deve dichiarare nella firma:

throws IOException

Il metodo chiamante dovrà quindi gestire l'eccezione tramite try-catch.

Risposta spiegata

Ragionamento

  1. leggiStudenti() fa una cosa sola: legge e restituisce le righe. Non stampa, non decide cosa fare in caso di errore.
  2. Files.readAllLines lancia IOException, che è checked: o la catturo o la dichiaro. Qui la dichiaro con throws IOException.
  3. Chi chiama (visualizzaStudenti, e nel bonus cercaStudente) mette la chiamata dentro try e scrive il catch (IOException e). Così ogni chiamante sceglie il suo messaggio.

Codice

// Punto 6: throws. Il metodo non gestisce l'errore, lo passa a chi lo chiama.
static List<String> leggiStudenti() throws IOException {
    return Files.readAllLines(FILE);
}

// nel chiamante, visualizzaStudenti():
try {
    ...
    List<String> studenti = leggiStudenti();
    ...
} catch (IOException e) {
    System.out.println("Impossibile leggere il registro.");
}

Errori da evitare

Se togli throws IOException e non metti nemmeno un try-catch, il programma non compila. Errore vero di javac:

SenzaGestione.java:7: error: unreported exception IOException; must be caught or declared to be thrown
        return Files.readAllLines(Path.of("studenti.txt"));
                                 ^
1 error

Il compilatore dice proprio le due strade: "must be caught" (try-catch) "or declared to be thrown" (throws).

7. Utilizzo di finally

Ripasso lampoIl blocco finally viene eseguito sempre, sia che il try vada a buon fine sia che scatti un catch. Teoria: try, catch e finally.
07Utilizzo di finally facile

Consegna. In almeno una delle operazioni utilizza un blocco finally.

Nel finally inserisci un messaggio che confermi la conclusione dell'operazione, ad esempio:

Operazione terminata.

Ricorda che il finally deve essere eseguito anche quando si verifica un'eccezione.

Risposta spiegata

Ragionamento

  1. La consegna chiede "almeno una" operazione; io l'ho messo in tutte e tre (inserisci, visualizza, cancella), come nell'esempio dell'Obiettivo finale dove "Operazione terminata." compare dopo ognuna.
  2. Il finally si scrive dopo l'ultimo catch.
  3. Nel try del menu invece non l'ho messo, perché nell'esempio del PDF dopo "Devi inserire un numero." non compare "Operazione terminata.".

Codice

try {
    controllaNome(nome);
    Files.writeString(FILE, nome + System.lineSeparator(),
            StandardOpenOption.CREATE, StandardOpenOption.APPEND);
    System.out.println("Studente inserito.");
} catch (IllegalArgumentException e) {
    System.out.println(e.getMessage());
} catch (IOException e) {
    System.out.println("Impossibile salvare lo studente nel registro.");
} finally {
    System.out.println("Operazione terminata.");   // sempre, con o senza errore
}

Output (pezzi delle sessioni vere)

Senza eccezione e con eccezione: "Operazione terminata." c'è in entrambi i casi.

Inserisci il nome dello studente: Mario Rossi
Studente inserito.
Operazione terminata.
Inserisci il nome dello studente:
Il nome non può essere vuoto.
Operazione terminata.

Perché funziona

Nel secondo caso controllaNome lancia l'eccezione, il try si interrompe, il catch stampa il messaggio e poi Java esegue comunque il finally. Il finally è il posto giusto per le cose che vanno fatte in ogni caso (nel capitolo di teoria: chiudere un file).

8. Più catch

Ripasso lampoDopo un try si possono mettere più catch: Java li prova dall'alto in basso e usa il primo compatibile. Teoria: L'oggetto Exception e più catch.
08Più catch medio

Consegna. Prevedi almeno un punto del programma in cui possano essere gestiti tipi diversi di eccezione.

Ad esempio:

try {
    // codice
} catch (NumberFormatException e) {
    // errore di conversione
} catch (Exception e) {
    // errore generico
}

I catch più specifici devono essere posizionati prima di quelli generici.

Risposta spiegata

Ragionamento

Nel programma ci sono due punti con più catch:

  1. Nel menu (main), esattamente lo schema del PDF: prima NumberFormatException (l'utente ha scritto lettere), poi Exception come rete di sicurezza per qualsiasi altro problema imprevisto, così il programma non si chiude mai di colpo.
  2. In inserisciStudente (e nel bonus cercaStudente): IllegalArgumentException per il nome vuoto e IOException per i problemi con il file. Sono due eccezioni "sorelle", nessuna è figlia dell'altra, quindi qui l'ordine non è obbligato.

Codice

} catch (NumberFormatException e) {
    // catch specifico: l'utente non ha scritto un numero
    System.out.println("Devi inserire un numero.");
} catch (Exception e) {
    // catch generico: qualsiasi altro errore imprevisto
    System.out.println("Errore imprevisto: " + e.getMessage());
}

Errori da evitare

Se inverti l'ordine e metti catch (Exception e) per primo, il programma non compila: Exception prende già tutto, quindi il catch di NumberFormatException sotto sarebbe irraggiungibile. Errore vero di javac:

OrdineCatch.java:7: error: exception NumberFormatException has already been caught
        } catch (NumberFormatException e) {
          ^
1 error

Risposta spiegata

Ragionamento

  1. Mettere insieme i pezzi dei punti 1–8: una costante FILE, uno Scanner condiviso, il main con il ciclo del menu e un metodo per ogni voce.
  2. Ogni metodo di operazione ha la stessa forma: try con il lavoro, uno o più catch con messaggi in italiano, finally con "Operazione terminata.".
  3. Dopo ogni operazione stampo una riga vuota e il menu ricompare. Nell'esempio del PDF il menu è scritto solo all'inizio per brevità ("indicativamente"), ma il punto 1 chiede di mostrarlo continuamente: nel programma vero ricompare ogni volta.

Codice

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
import java.util.List;
import java.util.Scanner;

public class RegistroStudenti {

    // Il file del registro: percorso relativo, cioè nella cartella da cui parte il programma
    static final Path FILE = Path.of("studenti.txt");
    static Scanner scanner = new Scanner(System.in);

    public static void main(String[] args) {
        boolean continua = true;

        while (continua) {
            stampaMenu();
            try {

Domande di verifica

10Domande di verifica domande

Consegna. Al termine dell'esercitazione rispondi alle seguenti domande:

  1. Qual è la differenza tra try, catch e finally?
  2. Perché NumberFormatException può essere utile nella gestione del menu?
  3. Qual è la differenza tra throw e throws?
  4. Perché IOException deve essere gestita o dichiarata?
  5. A cosa servono Path e Files?
  6. Qual è la differenza tra Files.readString() e Files.readAllLines()?
  7. Perché si utilizza StandardOpenOption.APPEND nell'inserimento degli studenti?
  8. Che cosa succede se si tenta di leggere un file che non esiste?
  9. Perché è utile utilizzare Files.exists() prima della lettura?
  10. Perché è importante avere catch specifici prima di un catch (Exception e)?
Risposte spiegate
  1. try contiene il codice che può dare errore; catch viene eseguito solo se nel try scatta un'eccezione del tipo indicato e la gestisce; finally viene eseguito sempre, con o senza errore. Nel registro: il try scrive sul file, il catch stampa "Il nome non può essere vuoto.", il finally stampa "Operazione terminata." in entrambi i casi.
  2. Perché la scelta arriva come testo (nextLine()) e l'utente può scrivere qualsiasi cosa. Se scrive abc, Integer.parseInt lancia NumberFormatException: catturandola stampo "Devi inserire un numero." e il menu ricompare, invece di far terminare il programma con un errore rosso.
  3. throw è un'istruzione che lancia un'eccezione adesso: throw new IllegalArgumentException("Il nome non può essere vuoto.");. throws sta nella firma di un metodo e avvisa che il metodo può lanciare quell'eccezione senza gestirla: static List<String> leggiStudenti() throws IOException. Uno la crea, l'altro la passa al chiamante.
  4. Perché è un'eccezione checked: rappresenta errori esterni al programma (file mancante, disco pieno, permessi) che possono capitare anche con codice perfetto, quindi il compilatore obbliga a pensarci. Se non la catturi né la dichiari, javac si rifiuta: "unreported exception IOException; must be caught or declared to be thrown" (errore vero, punto 6).
  5. Path rappresenta il percorso di un file (dove si trova, come si chiama): Path.of("studenti.txt"). Files è una classe di soli metodi static che lavorano sui file indicati da un Path: writeString, readAllLines, exists, deleteIfExists. Insieme sostituiscono File, FileWriter e FileReader, senza close().
  6. readString restituisce tutto il file in una sola String, a capo compresi; readAllLines restituisce una List<String> con un elemento per riga, senza a capo. Prova vera su un file con due nomi: 
    readString: [Mario Rossi
Luca Bianchi
]
readAllLines: [Mario Rossi, Luca Bianchi]
righe.size() = 2
    Per numerare gli studenti serve la lista, perciò il punto 3 usa readAllLines.
  7. Perché ogni nuovo studente deve essere aggiunto in fondo e non sostituire quelli già salvati. Senza opzioni writeString svuoterebbe il file a ogni inserimento. Va affiancato da CREATE, perché APPEND da solo su un file che non c'è lancia NoSuchFileException (prova vera al punto 2).
  8. Files.readAllLines lancia una NoSuchFileException, che è una sottoclasse di IOException. Prova vera: 
    Errore: java.nio.file.NoSuchFileException: non_esiste.txt
    Se nessuno la cattura, il programma si interrompe con lo stack trace.
  9. Perché il file mancante è un caso normale e prevedibile (all'inizio il registro non c'è mai): con un if lo si gestisce in modo chiaro e si dà un messaggio preciso, "Il registro non esiste ancora.", senza usare un'eccezione per una situazione ordinaria. Il try-catch resta per gli errori davvero imprevisti.
  10. Perché Java usa il primo catch compatibile: Exception è compatibile con tutto, quindi se fosse il primo i catch specifici non verrebbero mai usati e non potresti dare messaggi precisi ("Devi inserire un numero."). Infatti Java non compila nemmeno quel codice: "exception NumberFormatException has already been caught" (errore vero, punto 8).
